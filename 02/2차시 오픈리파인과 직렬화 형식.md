## 오픈리파인(OpenRefine)
- 학계나 관공서가 발표하는 대규모 데이터는 정제되지 않은 상태로 있는 경우가 많은데, 이를 깔끔하게 정리해 주는 데이터 정제 툴
- 크고 복잡한 스프레드시트 정리가 가능
- 데이터 집합에서 흔히 나타나는 일반적인 오류를 수정하고, 방대한 데이터에 섞인 불필요한 데이터를 정리
- 앞 차시의 수집 도구가 "모으는" 역할이라면, 오픈리파인은 모은 뒤의 "품질"을 담당

## 제이슨(JSON, JavaScript Object Notation)
- 인터넷에서 데이터를 주고받을 때 데이터를 표현하는 방식
- 기존 XML과 비슷하지만 용량이 작고 변환 속도가 빠름
- 데이터 종류에 제한이 없어 웹의 데이터를 정형화하는 데 사용
- JavaScript의 구문 형식을 따르지만 특정 프로그래밍 언어나 플랫폼에 독립적
- 텍스트로 되어 있어 사람과 기계 모두 읽고 쓰기 쉬움
- 언어·플랫폼 독립적이라 서로 다른 시스템 간 객체 교환이 쉽다

```json
{
  "id": 123,
  "name": "Bob",
  "email": "bob@example.com",
  "tags": ["flower", "jasmine"]
}
```

- 키와 값의 쌍, 배열, 중첩 구조로 표현하며 태그를 닫는 XML보다 짧게 쓸 수 있다

## 비슨(BSON, Binary JSON)
- JSON의 이진 표현 형식으로, 데이터 저장 엔진에서 활용
- JSON에 비해 속도가 빠르고 크기가 작음
- 다만 저장 공간 활용이 비효율적이고, 이를 지원하는 라이브러리가 많지 않음

## 쓰리프트(Thrift)
- 확장성 높은 이기종 언어 서비스를 지원하는 소프트웨어 프레임워크
- 기능
  - 복잡한 비정형 데이터 객체의 정형화
  - 정형화된 데이터를 취급하는 인터페이스
  - 응용 계층과 무관한 하부 데이터 형식 지원
- 특징: 버저닝 지원, 여러 언어 지원 및 언어별 소스 생성, 언어 간 직렬화, 동기·비동기 API, XML 설정 불필요, RPC 지원
- 단점: 라이브러리 API 업데이트가 잦고, XML 직렬화·역직렬화 기능이 없으며, 코드가 복잡함

## 프로토콜 버퍼스(Protocol Buffers)
- 구글 내부의 여러 시스템이 다양한 운영체제·언어 환경에서 통신할 수 있도록 만든 직렬화 방법을 오픈소스로 공개한 라이브러리
- XML에 비해 속도가 빠르고 데이터 크기가 작으며, 코드가 간단하고 개발이 쉬움
- 메시지를 연속된 비트로 만들고, 반대로 비트에서 원래 메시지를 복원할 수 있어 패킷 전송에 유용

```text
message Person {
  required int32 id = 1;
  required string name = 2;
  optional string email = 3;
}
```

```cpp
Person person;
person.set_id(123);
person.set_name("Bob");
person.set_email("Bob@example.com");

fstream out("person.pb", ios::out | ios::binary | ios::trunc);
person.SerializeToOstream(&out);
out.close();
```

- 순서: `.proto` 파일 작성 → 사용할 언어에 맞게 컴파일러로 컴파일 → 생성된 코드로 호출
- 언어별 클래스를 자동 생성하므로 필드 정의만 관리하면 된다

## 에이브로(Avro)
- 데이터 직렬화 시스템으로, Thrift·Protocol Buffers와 기능이 비슷함
- 스키마와 인터페이스 기능을 제공하고, 정의한 스키마를 데이터와 함께 전송
- 이 스키마는 JSON 파서 기능으로 정의
- 인코딩·디코딩 시 저장 공간을 많이 차지하고 성능을 떨어뜨린다는 단점
- 지원 언어: C, C++, Java, PHP, Python, Ruby 등

## 직렬화 형식 비교
| 항목 | JSON | BSON | Thrift | Protocol Buffers | Avro |
|---|---|---|---|---|---|
| 표현 | 텍스트 | 이진 | 이진+IDL | 이진+IDL | 이진+JSON 스키마 |
| 강점 | 호환성, 가독성 | 속도·크기 | 다언어 RPC | 속도·간결한 코드 | 스키마 동봉 전송 |
| 약점 | 크기 큼 | 저장 효율 낮음, 라이브러리 적음 | API 변경 잦음, 코드 복잡 | 스키마 컴파일 필요 | 인코딩·디코딩 비용 |
| 쓰는 곳 | 웹 데이터 교환 | MongoDB 저장 | 이기종 서비스 | 패킷·메시지 전송 | 이기종 데이터 교환 |

## 정리
- 정제(오픈리파인) → 표현(JSON) → 압축적 표현(BSON) → 언어 간 규격(Thrift/Protobuf/Avro) 순으로 필요가 생긴 흐름으로 보면 된다
- 형식 선택 기준은 세 가지: 사람이 읽어야 하는가, 크기·속도가 중요한가, 스키마를 함께 보내야 하는가
