## 빅데이터 수집·통합 기술의 배경
- 의미 있는 분석은 결국 데이터의 '양'에 의존하는데, 인터넷과 컴퓨터의 발전으로 정형·비정형 데이터를 대량으로 모을 수 있게 됨
- 그런데 모은 비정형 데이터를 처리하는 데 어려움이 생김
- 하둡: 구글의 소프트웨어에 기반해 방대한 데이터를 효과적으로 수집하고, 설치·사용이 쉬운 쪽으로 발전한 플랫폼

## 플럼(Flume)
- 이벤트 로그 데이터를 효율적으로 수집·집계하는 로그 수집기
- 안정성과 가용성이 높다는 점이 장점
- 클라이언트 여러 대에서 올라온 로그를 에이전트가 받아 HDFS에 적재하는 구조
  - 클라이언트 1~4 → 에이전트 1~3 → HDFS
- 즉 수집 지점과 저장 지점을 에이전트 계층으로 분리해, 클라이언트가 늘어나도 수집 쪽 구성을 그대로 확장할 수 있다

## 척와(Chukwa)
- 로그 데이터를 수집·분석·출력·모니터링하는 시스템
- 하둡 기반으로 동작하므로 **하둡이 반드시 설치되어 있어야** 함
- 응용 프로그램의 로그 저장 모듈을 수정하지 않아도 로그를 수집할 수 있음
- 하둡 분산 파일 시스템을 그대로 수용하고, 실시간 분석이 가능하다는 것이 장점

구성 요소는 수집·적재·확인 단계로 나뉜다.

| 구분 | 구성 요소 | 역할 |
|---|---|---|
| 수집 | 어댑터, 에이전트, Log4J Appender | 소스 노드의 로그 파일을 받아 올림 |
| 적재 | 컬렉터, 디먹스, 데이터싱크 | 모은 로그를 HDFS·MySQL·파일로 적재 |
| 활용 | MDL(Metrics Data Loader), 웹 UI, 커맨드라인 유틸리티 | 적재 결과를 조회·분석 |

- 적재된 데이터는 맵리듀스·스트리밍으로 분석

## 스크라이브(Scribe)
- 페이스북의 분산형 로그 수집 서버, 오픈소스 프로젝트
- 하루에 메시지 수십억 개를 저장할 수 있는 규모
- 중앙 서버 그룹과 노드당 Scribe 서버 한 대로 구성
- 기존 클라이언트를 수정하지 않아도 되는 크로스 플랫폼 클라이언트 라이브러리를 제공

## 스쿱(SQOOP, SQL-to-Hadoop)
- 기존 RDBMS의 데이터를 하둡으로 옮기려고 시작한 프로젝트
- JDBC 인터페이스를 쓰므로 MySQL, PostgreSQL, 오라클 등 다양한 DBMS를 지원
- Hive, Pig, HBase 같은 하둡 기반 프로젝트와 호환이 좋아 RDBMS와 NoSQL 사이의 연동에 많이 쓰임
- 2009년 5월 하둡 기여 모듈에서 출발해 2012년 3월 아파치 최상위 프로젝트(1.4.1)로 자리 잡음

## 하둡의 구성 요소
| 구성 요소 | 역할 |
|---|---|
| Hadoop Common | 다른 모듈을 지원하는 공통 컴포넌트 |
| HDFS | 여러 서버를 하나처럼 묶어 데이터를 분산 저장 |
| YARN | 병렬 처리를 위한 클러스터 자원 관리·스케줄링 |
| MapReduce | 분산 저장된 데이터를 병렬 처리하는 처리 모듈 |
| Ozone | 하둡을 위한 오브젝트 저장소 |

### 장단점
| 장점 | 단점 |
|---|---|
| 오픈소스라 라이선스 비용 부담이 적음 | HDFS에 저장된 데이터는 변경 불가 |
| 시스템을 멈추지 않고 장비 추가 가능(Scale Out) | 실시간 분석처럼 신속한 처리가 필요한 작업에는 부적합 |
| 일부 장비 장애가 전체 사용성에 미치는 영향이 작음(Fault Tolerance) | 버전이 너무 많고 지원(support)이 부실 |
| 저렴한 구축 비용, 비용 대비 빠른 처리 | 설정이 어려움 |
| 오프라인 배치 프로세싱에 최적화 | - |

## 카프카(Kafka)
- LinkedIn에서 시작한 아파치 프로젝트
- 확장성이 좋고 처리량이 높은 **분산 메시지 시스템**, 지속적이고 우수한 메시지 전달 성능을 보장
- 백엔드 서비스(생산자)와 프론트엔드, 트래킹 프록시가 카프카를 거쳐 하둡·DWH 쪽으로 흘러가는 토폴로지를 이룸
- 생산자와 소비자를 분리해 두어, 수집 대상이 늘어도 저장·분석 쪽을 다시 만들 필요가 없다

## 수집 도구 비교
| 항목 | Flume | Chukwa | Scribe | Kafka |
|---|---|---|---|---|
| 개발 | Cloudera | 야후 | 페이스북 | LinkedIn |
| 기반 | 자체 에이전트 | 하둡 필수 | 자체 서버 | 자체 브로커 |
| 강점 | 안정성·가용성 | 하둡 연동, 실시간 분석 | 대량 메시지, 클라이언트 수정 불필요 | 높은 처리량·확장성 |
| 성격 | 로그 수집 | 로그 수집·모니터링 | 로그 수집 서버 | 메시지 큐 |

## 정리
- 수집 계층은 "클라이언트를 고치지 않고 얼마나 많이, 안정적으로 받아오는가"가 핵심 비교 기준
- 저장은 HDFS, 적재 대상은 파일·MySQL·HDFS로 갈리며, 이후 처리는 맵리듀스로 이어진다
