## 왜 새로운 저장 기술이 필요했나
- 기존 데이터 저장 구조가 한계에 달함
- NoSQL은 기존 RDBMS의 ACID 트랜잭션(원자성·일관성·독립성·지속성)을 포기하는 대신 즉각적인 갱신이 가능한 저장소
- 분산 파일 시스템으로 데이터를 나눠 저장하면 신속하게 공급할 수 있어 처리 성능이 올라감

## CAP 이론
- 2002년 버클리대학 에릭 브루어 교수가 제시
- 분산 컴퓨팅 환경의 특성을 세 가지로 정의하고, 어떤 시스템이든 셋을 동시에 만족할 수 없으며 최대 두 가지만 만족할 수 있다고 봄

| 속성 | 의미 | 대표 시스템 |
|---|---|---|
| 일관성(Consistency) | 분산 환경에서 모든 노드가 같은 시점에 같은 데이터를 보여줘야 함 | RDBMS |
| 가용성(Availability) | 일부 노드가 다운되어도 다른 노드에 영향을 주지 않아야 함 | Bigtable, HBase, Cloudata |
| 지속성(Partition Tolerance) | 네트워크 전송 중 일부 데이터를 손실하더라도 시스템은 정상 동작 | Dynamo, Cassandra |

## RDBMS와 NoSQL

| 구분 | RDBMS | NoSQL |
|---|---|---|
| CAP 선택 | 일관성 + 가용성 | 지속성을 보장하고 일관성·가용성 중 하나를 포기 |
| 적용 사례 | 트랜잭션 ACID 보장(금융) | 대용량 분산 파일 시스템(C+P형), 비동기 서비스(A+P형: 아마존, 트위터) |
| 장점 | 데이터 무결성·정확성 보장, 정규화된 테이블, 소규모 트랜잭션 | 웹 환경의 다양한 정보를 검색·저장 가능 |
| 단점 | 확장성 한계, 클라우드 분산 환경에 부적합 | 무결성·정확성을 보장하지 않음 |
| 연산·특성 | UPDATE·DELETE·JOIN 가능, ACID 트랜잭션, 고정 스키마 | 수정·삭제 대신 입력으로 대체, 강한 일관성 불필요, 노드 추가·삭제와 데이터 분산에 유연 |

### NoSQL의 기술적 특성
- 무스키마: 고정된 스키마 없이 키 값을 이용해 다양한 형태의 데이터를 저장·접근. 저장 방식은 크게 열, 값, 문서, 그래프 네 가지
- 탄력성(Elasticity): 일부에 장애가 생겨도 클라이언트가 접근 가능하고, 다운타임 없이 대용량 데이터 생성·갱신, 규모·성능 확장이 용이하며 입출력 부하 분산에 유리
- 질의(Query): 수십~수천 대 규모에서도 데이터 특성에 맞게 검색·처리할 수 있는 질의 언어와 API를 제공
- 캐싱(Caching): 대규모 질의에도 고성능 응답을 주는 메모리 기반 캐싱이 중요하며, 개발·운영에 투명하게 적용되는 구조

### NoSQL 데이터 모델
| 모델 | 설명 | 제품 예 |
|---|---|---|
| 키-값 | 가장 단순한 구조, 범위 질의가 어렵고 응용 모델링이 복잡 | DynamoDB, S3 |
| 문서 | 문서마다 다른 스키마, 레코드 간 관계 설명 가능, 개념적으로 RDBMS와 유사 | SimpleDB, CouchDB, MongoDB |
| 열 기반 | 연관된 데이터 위주로 읽기에 유리, 같은 도메인 열 값이 연속되어 압축 효율이 좋고 범위 질의에 유리. 레코드 하나를 바꾸려면 여러 곳을 수정해야 함 | Cassandra |

## S3(Simple Storage Service)
- 아마존의 인터넷 스토리지 서비스로, 웹에서 용량과 관계없이 데이터를 저장·검색하는 웹 서비스 인터페이스를 제공
- 확장성과 신뢰성을 갖춘 비용 효율적 인프라를 쓰게 해 줌
- 기능
  - 객체 크기 최소 1바이트~최대 5TB의 읽기·쓰기·삭제, 객체 수 제한 없음
  - 객체는 버킷에 저장되고 개발자가 정한 고유 키로 검색
  - 버킷은 여러 지역 중 한 곳에 저장 가능하며, 지연 시간 최적화·비용 최소화·규정 준수에 따라 지역 선택
  - 미국 표준 지역은 네트워크 맵으로 요청을 버지니아 북부나 태평양 연안 북서부로 라우팅
  - 저장한 객체는 사용자가 옮기지 않는 한 해당 지역 밖으로 이동하지 않음
  - 인증 메커니즘, 공개/비공개 설정, 사용자별 권한 부여
  - 업로드·다운로드 보안 옵션과 데이터 암호화, 표준 기반 REST/SOAP 인터페이스
  - 기본 다운로드 프로토콜은 HTTP이며 대규모 배포 비용 절감용 비트토렌트 인터페이스 추가 제공
  - 반복 삭제(기간 경과 후 규칙으로 제거), 일회성 삭제(단일 요청으로 최대 1000개)
- 활용: 콘텐츠 저장·배포, 데이터 분석용, 백업·보관·복구

## HDFS(Hadoop Distributed File System)
- 하둡은 아파치 진영에서 분산 환경 컴퓨팅을 목표로 시작한 프로젝트이며, 분산 처리 환경의 필수 조건인 파일 시스템으로 HDFS를 제공
- 마스터 하나(NameNode)와 슬레이브 여러 개(DataNode)로 클러스터 구성
- 대용량 파일을 여러 블록으로 나눠 분산 저장, 마지막 블록을 제외하면 블록 크기는 동일하며 기본 64MB
- 데이터 복제 기법 지원

동작 구조
- 클라이언트는 NameNode에 메타데이터(파일명, 복제 개수 등)를 요청
- 실제 읽기·쓰기는 DataNode의 블록 단위로 이루어지고, 랙을 넘어 복제본이 유지됨
- NameNode는 "어디에 무엇이 있는가"만 알고, 데이터 자체는 DataNode가 가진다

## 다이나모DB
- 아마존 웹에서 유·무료로 서비스
- 하드웨어 프로비저닝, 복제, 설정 패치, 응용에 따른 DB 자동 분할을 지원
- 원하는 만큼 DB를 만들거나 지우며 데이터를 저장, 모든 데이터는 SSD에 저장
- 데이터 모델: 테이블 - 항목(Item) - 속성(Attribute), 속성 값은 문자열·숫자·바이너리·집합
- 기본키가 항목을 구분하며, 테이블의 모든 항목은 동일한 기본키 체계를 쓰고 각 항목의 기본키 값은 고유해야 함
- 항목마다 다른 속성을 가질 수 있어 스키마가 유연함

## 몽고DB(MongoDB)
- 신뢰성과 확장성에 기반한 문서 지향 데이터베이스
- 방대한 데이터에서 낮은 관리 비용과 사용 편의성을 목표로 10gen이 오픈소스로 개발, 상업적 지원 가능
- 저장의 최소 단위는 문서이며, 문서들은 RDBMS 테이블에 해당하는 컬렉션에 모이고 컬렉션은 DB에서 관리
- 자동 샤딩(Auto-Sharding)으로 분산 확장, 샤딩은 데이터를 나눠 다른 서버에 저장하는 과정
- 범위 질의, 보조 인덱스, 정렬, 맵리듀스 집계를 지원
- 데이터는 BSON 형태로 저장, C++로 작성
- 용량이 부족하면 샤드 노드를 추가해 자동으로 재분산
- 구성: 응용 서버 → 라우터(Mongos) → 설정 서버(configsvr) + 샤드(MongoDB 1~3)

## 카우치DB(CouchDB)
- 인터페이스가 JavaScript로 구성된 문서 기반 데이터베이스
- MongoDB보다 질의, 확장성, 버전 관리에서 성능이 더 우수하다고 평가
- 데이터가 여러 시점에 접근할 때 생기는 문제를 다중 버전 동시 동작 제어로 해결
- 단점: 쓰기 작업 중 충돌이 나면 다른 기술보다 클라이언트 부하가 커짐
- 아파치 프로젝트 중 유일하게 얼랭(Erlang)을 사용하고, 데이터 표현은 JSON 파서를 사용
- 양방향 복제와 맵리듀스를 지원해 오프라인 사용 후 동기화가 가능
- 충돌을 예외 상황으로 구분하지 않고 충돌 문서도 일반 문서와 똑같이 복제·보안 적용
- 전체 텍스트 검색 API, 뷰 인덱스, 확장 가능한 보안 모델 지원

## 카산드라(Cassandra)
- 키-값 구조의 DBMS로 페이스북에 적용하다 2008년 구글을 통해 오픈소스로 배포
- 토큰 링 기반의 키 구간이 설정되어 노드 추가·제거만으로 저장 공간을 유연하게 확장·축소
- 다른 노드에 복제본을 두어 특정 노드 장애에도 서비스 영향과 데이터 유실이 없음
- 수정·추가·삭제 시 실제 스토리지에 적용하기 전에 CommitLog에 먼저 기록하므로 MySQL 대비 8~15배 빠른 성능
- 1차 인덱스는 열 집합의 열 이름, 2차 인덱스는 열의 값을 기반
- 데이터 전송 프로토콜로 Thrift를 사용해 언어에 의존하지 않고 쓸 수 있음
- 물리 파일은 SSTable(Sorted String Table)로 저장되고 1차 정렬 조건에 맞춰 사전 정렬된 형태를 유지

## 정리
- CAP에서 무엇을 포기했는지가 제품 성격을 결정한다: 일관성 포기(Cassandra, DynamoDB) → 가용성·확장성, 일관성 유지(RDBMS) → 무결성
- 파일 저장이면 S3·HDFS, 항목 저장이면 키-값·문서·열 기반으로 나눠 고르면 된다
