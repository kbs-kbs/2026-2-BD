## H베이스(HBase, Hadoop database)
- 행, 열 그룹, 열 이름, 타임스탬프를 이용한 테이블 구조
- 하둡 파일 시스템 위에 설치되고, 노드 관리는 주키퍼(ZooKeeper)가 맡음
- 각 프로세스는 자신의 레코드를 비동기적으로 갱신
- 영역 서버(Region Server) 간 시스템 대체 작동, 불량 클러스터 복구 기능 지원
- 동작은 Get / Put / Scan / Delete 네 가지
- 읽기·수정과 맵리듀스 연산을 함께 지원하고, 즉시 실행과 일괄 처리를 모두 다룸
- 데이터 모델은 열 집합 기반 저장소

### 저장 구조
- 논리적으로는 하나의 행에 여러 열이 모여 보이지만, 물리적으로는 **열 그룹 단위로 따로 저장**됨
  - 예: `com.cnn.www` 행의 `contents:` 열, `anchor:` 열, `mine:` 열이 각각 다른 물리 파일로 나뉨
- 논리 저장 공간(행 키 + 타임스탬프 + 열 이름별 값)과 물리 저장 공간(열 그룹별 파일)이 다르다는 점이 HBase 이해의 핵심
- 구성: HMaster, ZooKeeper, HRegionServer, HLog, HDFS
  - 쓰기는 MemStore에 쌓였다가 storefile(HFile)로 내려가고, 유실 대비용으로 HLog를 함께 씀

## 레디스(Redis, Remote Dictionary System)
- 메모리 기반의 키-값 저장 공간으로, NoSQL 또는 인메모리 솔루션으로 분류
- 다양한 데이터 구조를 지원
- 메모리에 저장한 내용을 유지하려고 파일로 싱크하는 기능을 제공

| 데이터 타입 | 설명 |
|---|---|
| String | 일반 문자열, 최대 512MB. 숫자와 JPEG 같은 바이너리 파일도 저장 |
| Set | 문자열의 집합. 교집합·합집합·차집합 연산을 빠르게 얻을 수 있음 |
| Sorted Set | 가중치(score)가 붙은 집합, 내부가 오름차순 정렬. score 범위 질의·톱랭킹 질의 가능 |
| Hash | 값 내부의 필드-문자 쌍. RDBMS의 기본키 하나와 문자열 필드 하나로 된 테이블에 해당 |
| List | 문자열 집합이지만 양방향 연결 리스트. 앞·뒤에서 push/pop, 지정 인덱스 위치에 삽입·삭제 |

### 저장 구조
- 최상위 키 아래에 문자열 값, 리스트(입력 순서 유지, top/tail에서 삽입·선택), 집합(입력 순서), 정렬 집합(score 값 기준 정렬), 해시(필드별 값)가 붙는 형태
- 즉 키 하나에 자료 구조 하나를 통째로 담는 모델이라, 관계를 조인으로 푸는 대신 구조를 미리 정해 쓰는 방식

## 리악(Riak)
- DynamoDB 계열에 속함
- 데이터 모델은 키-값이지만 값에 JSON 문서가 저장되는 문서 지향 형식
- 구성
  - 노드: 물리적인 서버
  - v노드: 논리적인 서버(파티션)
  - 링 형태의 데이터 분산 저장 구조가 클러스터링 단위를 재배포
- 링을 돌리는 중에도 노드 추가·삭제로 동적 재설정이 가능하고, 상황이 생기면 변형된 링 구조에 따라 데이터를 자동 재배포
- 2^160 크기의 링을 v노드 개수로 나눠 담당 구간을 정하고, 키를 해시해 위치를 찾음

## 하이퍼테이블(Hypertable)
- C++ 언어로 개발
- 열 그룹과 타임스탬프 개념을 사용
- HQL이라는 SQL과 비슷한 명령어를 제공해 RDBMS와 기능이 비슷
- C++ API를 완벽하게 제공하며, Java로 개발된 HBase보다 성능이 뛰어남
- 구성: 마스터(예비 마스터 포함), 범위 서버, DFS 브로커, 분산 파일 시스템(HDFS, MapR, Ceph, 로컬 등)

## 주키퍼(ZooKeeper)
- 하둡의 분산 처리 시스템(Hadoop, Chukwa, Pig 등)을 일괄적으로 관리하는 시스템
- 다중 서버 집합을 묶어 관리해 주는 야후의 분산 코디네이터
- 분산 처리 시스템의 장애 문제를 해결하려고 개발
- 서버 여러 대 중 하나가 Leader가 되어 클라이언트 요청을 중계하는 구조

## 볼드모트(Voldemort)
- LinkedIn에서 개발
- Java 기반의 키-값 저장 형식으로 일종의 해시 테이블
- 복잡한 구조의 백엔드로, 분산 대형 클러스터 환경에서 동작
- 일관성 있는 해싱으로 키와 관련된 저장 위치를 빠르게 조회
- 버전을 제어해 일치하지 않는 값을 신속히 처리
- 여러 클라이언트가 거의 동시에 여러 값을 기록할 때, 한 번의 읽기 연산으로 그 값을 처리

## 저장 기술 비교
| 기술 | 모델 | 기반 | 강점 | 주의점 |
|---|---|---|---|---|
| HBase | 열 집합 | HDFS + ZooKeeper | 대용량 희소 테이블, 일괄·즉시 처리 | 행 단위 트랜잭션 아님, 열 그룹 설계 중요 |
| Redis | 키-값(자료 구조) | 메모리 | 응답 속도, 자료 구조 연산 | 메모리 용량, 영속화 설정 필요 |
| Riak | 키-값(문서) | 링 분산 | 노드 추가·삭제 유연 | 범위 질의 약함 |
| Hypertable | 열 집합 | HDFS 등 | HQL, C++ 성능 | 생태계가 HBase보다 작음 |
| Voldemort | 키-값(해시) | 일관성 해싱 | 빠른 조회, 동시 쓰기 처리 | 복잡한 질의 불가 |
| ZooKeeper | 관리(코디네이터) | 자체 앙상블 | 분산 시스템 조정·장애 대응 | 데이터 저장소로 쓰는 용도 아님 |

## 정리
- 열 기반 계열(HBase, Hypertable)은 "행 전체를 한 파일에 넣지 않는다"는 점을 기억하면 구조가 정리된다
- 레디스는 저장소라기보다 자료 구조 서버에 가깝고, 나머지 키-값 계열은 해시로 위치를 찾는 방식이 공통점
- ZooKeeper는 저장 기술이라기보다 위 기술들을 묶어 주는 관리 계층이다
